# n8n Workflow Best Practices — Sources

Provenance for [`../SKILL.md`](../SKILL.md). This file is deliberately kept
out of the skill body so it costs no tokens at load time; read it to verify a
rule, not to follow one. Repository-wide provenance tiers and known gaps:
[SOURCES.md](../../../SOURCES.md).

Throughout this file, "this document" and section references like §4 point to
`../SKILL.md`, whose rules these sources support. This text was moved out of that
file verbatim, so "the rules above" likewise means the rules there.

Entries dated 2026-09-28 were added when SKILL.md was trimmed that day, to back
facts the trim introduced; their § numbers refer to the trimmed file. The
`n8n source` entries link to the last commit that touched each file on `master`
as of 2026-09-28 (latest release that day: `n8n@2.40.7`). Where a source
qualifies or contradicts a rule, the entry records what the source says.


This document synthesizes n8n's own docs plus current (2026) community and
production guidance. Primary sources used while writing it:

- [n8n Docs — Error Trigger node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger) — official Error Trigger behavior and setup. Re-read for §4 and §7: the error workflow is created "with the Error Trigger as the first node"; "If a workflow uses the Error Trigger node, you don't have to publish the workflow" (n8n 2.x says *publish* where SKILL.md says *active*); and "You can't test error workflows when running workflows manually. The Error Trigger only runs when an automatic workflow errors" (checked 2026-09-28).
- [n8n Blog — Creating error workflows in n8n](https://blog.n8n.io/creating-error-workflows-in-n8n/) — official guidance on wiring an Error Workflow per production workflow.
- [n8n Docs — Pin and mock data](https://docs.n8n.io/build/work-with-data/pin-and-mock-data) — official pinned-data testing workflow; the source for pinning being a development-only feature that "isn't available for production workflow executions" (checked 2026-08-20).
- [n8n Docs — Webhook node, workflow development](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/workflow-development) — test and production webhook URLs are separate endpoints; the test URL stays active for 120 seconds and production traffic is not visible in the editor (checked 2026-08-20).
- [n8n Docs — Set a custom encryption key](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key) — the source for n8n creating "a random encryption key automatically on the first launch" and saving it in `~/.n8n` (checked 2026-08-20).
- [n8n Docs — Handle errors gracefully](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully) — the error workflow is chosen per workflow in **Workflow Settings**, "runs if an execution fails", "must start with the Error Trigger", and "You can use the same error workflow for multiple workflows" (§4, first bullet). It also qualifies §4's no-fire rule: when "the error is caused by the trigger node of the main workflow", the error workflow still runs and receives a `trigger{}` payload carrying a `WorkflowActivationError`. Only a workflow that stops running without an error goes unreported (checked 2026-09-28).
- [n8n Docs — Work with nodes: Node settings](https://docs.n8n.io/build/understand-workflows/workflow-components/work-with-nodes#node-settings) — the node's **On Error** setting and its options **Stop Workflow**, **Continue** ("using the last valid data") and **Continue (using error output)** ("passing error information to the next node for potential handling"): the source for §4's `On Error` and `Continue (using error output)`. The page names no "Continue On Fail" setting; the mapping from that legacy flag is confirmed in source below. It describes **Retry On Fail** only as "When an execution fails, the node reruns until it succeeds" and says nothing about backoff (checked 2026-09-28).
- [n8n Docs — Stop And Error](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.stopanderror) — "Use the Stop And Error node to display custom error messages, cause executions to fail under certain conditions, and send custom error information to error workflows": the node §4 ends a non-recovery error branch with (checked 2026-09-28).
- [n8n Docs — Types of executions](https://docs.n8n.io/build/understand-workflows/understand-executions/types-of-executions) — "The execution flow for production executions doesn't display in the Editor tab of the workflow as with manual executions. Instead, you can see executions in the workflow's **Executions** tab according to your workflow settings": the source for §7's production-URL runs appearing under Executions rather than on the canvas. Also "Production executions ignore all pinned data", which corroborates §7's pin rule (checked 2026-09-28).
- [n8n Docs — Executions environment variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions) — `EXECUTIONS_DATA_PRUNE` (Boolean, default `true`, "Whether to delete data of past executions on a rolling basis") and `EXECUTIONS_DATA_MAX_AGE` (Number, default `336`, "The execution age (in hours) before it's deleted"), the two variables in §5's retention bullet. Pruning is already on by default, so the choice the rule forces is the maximum age. Both are self-hosted settings (checked 2026-09-28).
- [n8n Docs — n8n metadata](https://docs.n8n.io/build/code-in-n8n/use-built-in-shortcuts/n8n-metadata) — `$env` "Contains n8n instance configuration environment variables" and is listed as usable in expressions and the Code node: the `$env` expression §5 bans as a route for secrets (checked 2026-09-28).
- [n8n Docs — v2.0 Breaking changes](https://docs.n8n.io/changelog/v20-breaking-changes) — "The new workflow publishing system replaces the previous active/inactive toggle", so n8n 2.x's UI and docs say *publish/unpublish* where SKILL.md §4 and §8 say *active/deactivated* (the CLI's `--activeState` flag keeps the old term). Also "The default value for `N8N_BLOCK_ENV_ACCESS_IN_NODE` is now set to `true`". The [Security environment variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security) page still lists that variable's default as `false`; the env-provider source entry below sides with `true`. Either way §5's `$env` ban stands, because an operator can unblock access (checked 2026-09-28).
- [n8n Docs — Use the command line](https://docs.n8n.io/deploy/host-n8n/configure-n8n/use-the-command-line) — the Server CLI flags in §8: `export:workflow --all`, `--output` and `--separate` ("Exports one file per workflow (useful for versioning). Must set a directory using --output"); `import:workflow --separate` ("Imports `*.json` files from directory provided by --input") with `--input`; and `--help` on every command. `--activeState` "Accepts `false` (default, deactivates all imported workflows) or `fromJson`", and the page adds that `fromJson` is "only supported in multi-main & queue mode". Also on the page: `export:workflow --published` exports the published version "instead of the current draft", so a plain export captures drafts; import overwrites workflows that have the same IDs; a known bug keeps a previously active workflow's cron triggers running after import on non-multi-main instances until restart; and the Server CLI runs only on self-hosted n8n (checked 2026-09-28).
- [n8n Docs — Export and import](https://docs.n8n.io/build/manage-workflows/export-and-import) — "Exported workflow JSON files include credential names and IDs" (§5's reference shape; the key and field names are confirmed in source below), and HTTP Request nodes imported from cURL "may contain authentication headers". Volatile: n8n recommends its newer n8n CLI (`.n8np` packages) over the Server CLI export and import commands §8 uses, and plans to deprecate those, "though this is not yet scheduled" (checked 2026-09-28).
- [n8n source — `packages/cli/src/commands/export/workflow.ts`](https://github.com/n8n-io/n8n/blob/0d465d4428319d2d546a62f42f9f0fbae83f26fe/packages/cli/src/commands/export/workflow.ts) — with `--separate`, each workflow is written to `<output>/<workflow id>.json` (§8's "one `<id>.json` per workflow"). Output is `JSON.stringify` with no indentation unless `--pretty` is passed, which is the serialization §6 says to keep. Without `--published` or `--version`, each workflow's current `versionId` (its draft) is exported (checked 2026-09-28).
- [n8n source — `packages/cli/src/commands/import/workflow.ts`](https://github.com/n8n-io/n8n/blob/0b9c174d1ae382b7680b27fcee581cbe74fbc112/packages/cli/src/commands/import/workflow.ts) — `--activeState` accepts `false` or `fromJson` and defaults to `'false'`, described as "deactivates all imported workflows"; `fromJson` "activates/deactivates each workflow based on its JSON active field", which is §8's "keeps each file's state". `--activeState=fromJson` throws unless the instance runs in queue mode: "can only be used when n8n is running in queue or multi-main mode. In regular deployment mode, workflow activation is not supported" (checked 2026-09-28).
- [n8n source — `packages/workflow/src/interfaces.ts`](https://github.com/n8n-io/n8n/blob/c6fb5737c17d1edbface702b8dc6aab0e1a33914/packages/workflow/src/interfaces.ts) and [`node-execution-context.ts`](https://github.com/n8n-io/n8n/blob/de238f3dde9affc02abd1a28ab2d932afeda1e91/packages/core/src/execution-engine/node-execution-context/node-execution-context.ts) — a node's `credentials` is a map of `INodeCredentialsDetails { id: string | null; name: string }`, looked up by credential type (`node.credentials?.[type]`): §5's `credentials.<type>: {id, name}`. `IWorkflowSettings.errorWorkflow` holds the error workflow's ID and is the field §8's `jq` gate reads. `INode.onError` is `'continueErrorOutput' | 'continueRegularOutput' | 'stopWorkflow'`, alongside the legacy `continueOnFail` boolean. Retry is configured by `retryOnFail`, `maxTries` and `waitBetweenTries` (checked 2026-09-28).
- [n8n source — `ndv.utils.ts`](https://github.com/n8n-io/n8n/blob/a0535781a7fa8ee47ffb9902b8b2163ba3a5f199/packages/frontend/editor-ui/src/features/ndv/shared/ndv.utils.ts) and [`base-execute-context.ts`](https://github.com/n8n-io/n8n/blob/f3fea3b8b8cfe7eec2f3625e6f11a2e58edc2d82/packages/core/src/execution-engine/node-execution-context/base-execute-context.ts) — the editor maps a legacy `continueOnFail: true` onto `onError: 'continueRegularOutput'`, and at run time `continueOnFail()` reads `onError` first, falling back to the legacy flag only when `onError` is unset. This is the basis for §4's "`On Error` → `Continue` (the legacy `Continue On Fail`)". `ndv.utils.ts` also limits the editor's `maxTries` field to 2–5 (default 3) and `waitBetweenTries` to 0–5000 (default 1000) (checked 2026-09-28).
- [n8n source — `packages/frontend/@n8n/i18n/src/locales/en.json`](https://github.com/n8n-io/n8n/blob/4263117b480a36510c2491aae0114e93175900b0/packages/frontend/@n8n/i18n/src/locales/en.json) — the editor's labels for §4's node settings. **On Error** offers **Stop Workflow** ("Halt execution and fail workflow"), **Continue** (`continueRegularOutput`, "Pass error message as item in regular output") and **Continue (using error output)** (`continueErrorOutput`, "Pass item to an extra `error` output"). The retry settings are **Retry On Fail**, **Max. Tries** (with a period: "Number of times to attempt to execute the node before failing the execution") and **Wait Between Tries (ms)** (checked 2026-09-28).
- [n8n source — `StopAndError.node.ts`](https://github.com/n8n-io/n8n/blob/ea5b874a8c88f1bd13c6c1e5633f79ad1b6449d9/packages/nodes-base/nodes/StopAndError/StopAndError.node.ts) — the node's display name is `Stop and Error` (the docs title it "Stop And Error"); it has no outputs, and `execute` always throws a `NodeOperationError` built from its message or error object (checked 2026-09-28).
- [n8n source — `packages/cli/src/workflow-helpers.ts`](https://github.com/n8n-io/n8n/blob/3aa9179424c397a27208b528160805553b9e0c29/packages/cli/src/workflow-helpers.ts) — `removeDefaultValues` deletes `errorWorkflow` when it holds the editor's `'DEFAULT'` ("no workflow") placeholder (added by PR #24299, merged 2026-01-15). A workflow with no error workflow therefore has no `settings.errorWorkflow` key, which is what §8's `== null` check relies on (checked 2026-09-28).
- [n8n source — `packages/core/src/execution-engine/workflow-execute.ts`](https://github.com/n8n-io/n8n/blob/40b6d84525c1489acae9752b91fb69a62727cc96/packages/core/src/execution-engine/workflow-execute.ts) — `getRetryParams` clamps **Retry On Fail** to 2–5 tries (default 3) with a fixed wait of 0–5000 ms between them (default 1000 ms). There is no backoff, so a retry rule that promises backoff does not describe n8n. The retry loop catches whatever the node throws and re-runs it, with no check of the error's class or HTTP status; the only error not retried is a sub-workflow error a node resumes with. That is §4's "retries every error, 4xx included". A continued error (`continueOnFail`, `continueRegularOutput` or `continueErrorOutput`) is stored on the node's run data, not on the execution's `resultData.error`, and the run goes on. But the engine clears its pending error only when the next node starts, so a node that throws as a whole and is the last to run still ends the execution with status `error` and `resultData.error` set. This qualifies §4's claim that a continued error does not fail the execution: it holds except in that last-node case. Reproduced the same day in a scratch directory against the published `n8n-core@2.40.3` engine (the version `n8n@2.40.7` depends on), using stub node types. A node throwing a `NodeApiError` with `httpCode: '404'` under **Retry On Fail** ran 4 times with `maxTries: 4`, and a throwing node ran 5 times with `maxTries: 9`. A throwing node under either **Continue** mode ended the execution `success` when another node followed it and `error` when it was last. A node that returns per-item error items (the `continueOnFail()` pattern) ended it `success` either way. Under **Continue (using error output)**, a node that throws as a whole passed its input down the regular output, not the `error` output: only per-item error items reach the error branch (checked 2026-09-28).
- [n8n source — `workflow-execute.test.ts`](https://github.com/n8n-io/n8n/blob/898480070f22aa9abc63340c04cd4f8eeaea6ab3/packages/core/src/execution-engine/__tests__/workflow-execute.test.ts) — for an Execute Workflow node that resumes with a sub-workflow's error and has a node after it, the engine's tests expect `status` `success` and `resultData.error` undefined under `continueErrorOutput` (error item on the `error` output), `continueRegularOutput` and legacy `continueOnFail` (error item in `json.error`). Under `stopWorkflow` they expect `status` `error` with the error on `resultData.error` (checked 2026-09-28).
- [n8n source — `packages/cli/src/execution-lifecycle/execute-error-workflow.ts`](https://github.com/n8n-io/n8n/blob/1f19b11c403b97cd84718e2cbede6f485481058f/packages/cli/src/execution-lifecycle/execute-error-workflow.ts) — `executeErrorWorkflow` runs the error workflow only `if (fullRunData.data.resultData.error !== undefined)`, so a continued error that leaves `resultData.error` unset never reaches it. A `Stop and Error` node's throw, under the default `stopWorkflow`, does set it: in the local run above, a stub node throwing a `NodeOperationError` (what `Stop and Error` throws) with no `On Error` override ended the execution `error` with the error on `resultData.error`. Together these are the basis for §4's continued-error rule (checked 2026-09-28).
- [n8n source — `packages/cli/src/active-workflow-manager.ts`](https://github.com/n8n-io/n8n/blob/6c4135ddfb59f4ce3feec71559e343289e5c0b36/packages/cli/src/active-workflow-manager.ts) — when a trigger node fails, n8n removes the workflow's triggers, raises a `WorkflowActivationError` ("The workflow was deactivated because its trigger node ... failed"), runs the error workflow, and queues a reactivation attempt. A deactivation caused by a trigger failure therefore does reach the Error Workflow; a workflow that stops without an error never does. The file dispatches the error workflow only on a trigger failure and on a failed activation at startup. `remove()` clears a workflow's webhooks and triggers without running it, and it is what `deactivateWorkflow` in [`workflow.service.ts`](https://github.com/n8n-io/n8n/blob/3aa9179424c397a27208b528160805553b9e0c29/packages/cli/src/workflows/workflow.service.ts) calls when the workflow publication service is off. With that service on, [`workflow-trigger-activator.ts`](https://github.com/n8n-io/n8n/blob/378e9265849fb09d53dac8475e07fabec177ef44/packages/cli/src/workflows/triggers/workflow-trigger-activator.ts) likewise runs the error workflow only from `recoverFromRuntimeTriggerFailure`, never from `deactivate`. Together these back §4's "deactivated by hand" (checked 2026-09-28).
- [n8n source — `packages/workflow/src/workflow-data-proxy-env-provider.ts`](https://github.com/n8n-io/n8n/blob/0ffd76093c2e9b62098e14dc7e402f727e14e027/packages/workflow/src/workflow-data-proxy-env-provider.ts) — environment access is blocked unless `N8N_BLOCK_ENV_ACCESS_IN_NODE` is exactly `'false'`, and a blocked `$env` read throws "access to env vars denied" (checked 2026-09-28).
