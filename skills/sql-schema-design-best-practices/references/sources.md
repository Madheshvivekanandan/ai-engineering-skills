# SQL Schema Design Best Practices — Sources

Provenance for [`../SKILL.md`](../SKILL.md). This file is deliberately kept
out of the skill body so it costs no tokens at load time; read it to verify a
rule, not to follow one. Repository-wide provenance tiers and known gaps:
[SOURCES.md](../../../SOURCES.md).

Throughout this file, "this document" and section references like §4 point to
`../SKILL.md`, whose rules these sources support. This text was moved out of that
file verbatim, so "the rules above" likewise means the rules there.


Primary sources retrieved and read while writing this document. PostgreSQL pages were read from their `/docs/current/` URLs and self-reported PostgreSQL 18; if you target an older major version, re-verify each feature against that version's documentation. Where a version difference is load-bearing enough to break a migration — `uuidv7()` availability (section 3) and implicit `BUFFERS` (section 7) — it is flagged at the rule itself rather than only here.

- [PostgreSQL Documentation — 5.5. Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) — `CHECK` satisfied by true or null, "in most database designs the majority of columns should be marked not null", `UNIQUE` null handling and `NULLS NOT DISTINCT`, referential actions, `MATCH FULL`, the note that foreign keys do not index the referencing columns, the ban on cross-row `CHECK`, and `EXCLUDE` constraints.
- [PostgreSQL Documentation — 5.3. Identity Columns](https://www.postgresql.org/docs/current/ddl-identity-columns.html) — `GENERATED ALWAYS` vs `BY DEFAULT`, implicit `NOT NULL`, and the explicit statement that identity does not itself guarantee uniqueness.
- [PostgreSQL Documentation — 8.1. Numeric Types](https://www.postgresql.org/docs/current/datatype-numeric.html) — `numeric` recommended for monetary amounts, float inexactness and equality comparison, and the exact integer and `numeric` limits (trimmed from SKILL.md 2026-09-28).
- [PostgreSQL Documentation — 8.5. Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html) — `timestamptz` converting input to UTC, `timestamp` silently discarding zone information, the recommendation against `time with time zone`, storage sizes and resolutions, and why `interval` stores months/days/microseconds separately.
- [PostgreSQL Documentation — 8.14. JSON Types](https://www.postgresql.org/docs/current/datatype-json.html) — prefer `jsonb`, keep a somewhat fixed structure, whole-row locking on update, `jsonb_ops` vs `jsonb_path_ops`, expression indexes on extracted subdocuments, and the rejected value types. Re-read 2026-09-28 (self-reported PostgreSQL 18.6), after the trim replaced "supports fewer operators" with an explicit list (verified retroactively): the page says "the `jsonb_path_ops` operator class supports only queries with the `@>`, `@?` and `@@` operators", and that its index is "usually much smaller" than a `jsonb_ops` index with searches that "typically perform better". That is the basis for the operator list in section 5. The same reading confirms the rejected values as section 5 now spells them: `jsonb` "rejects `\u0000`", and "`NaN` and `infinity` values are disallowed".
- [PostgreSQL Documentation — 9.2. Comparison Functions and Operators](https://www.postgresql.org/docs/current/functions-comparison.html) — read 2026-09-28 (self-reported PostgreSQL 18.6), after the trim added the function to section 2 (verified retroactively). Table 9.3 documents `num_nonnulls ( VARIADIC "any" ) → integer`, which "Returns the number of non-null arguments". This is the function in the polymorphic-parent `CHECK (num_nonnulls(order_id, invoice_id) = 1)` in section 2. The page does not show that usage; the PostgreSQL 9.6 release notes below do.
- [PostgreSQL Documentation — 9.14. UUID Functions](https://www.postgresql.org/docs/current/functions-uuid.html) — the documented generators `gen_random_uuid()`, `uuidv4()` and `uuidv7()`, and `uuidv7()` being time-ordered. The PostgreSQL 17 version of this page ([/docs/17/](https://www.postgresql.org/docs/17/functions-uuid.html)) documents only `gen_random_uuid()`, which is the basis for the availability caveat in section 3.
- [PostgreSQL Documentation — 11.1. Indexes: Introduction](https://www.postgresql.org/docs/current/indexes-intro.html) — index maintenance overhead on every data modification, unused indexes preventing heap-only tuple updates and therefore warranting removal, the need to run `ANALYZE` regularly, and plain `CREATE INDEX` blocking writes.
- [PostgreSQL Documentation — 11.3. Multicolumn Indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html) — which access methods support multiple key columns, where column order matters, the 32-column maximum, "indexes with more than three columns are unlikely to be helpful unless the usage of the table is extremely stylized", and the B-tree skip scan optimization that can sometimes serve a query whose predicate omits the leading column when that column has few distinct values. The PostgreSQL 17 version of this page ([/docs/17/](https://www.postgresql.org/docs/17/indexes-multicolumn.html)), read 2026-09-28 (self-reported 17.11), has no skip scan text. It says a query with no constraint on the leading column needs "the entire index" scanned, and that constraints to the right of the leading columns "do not reduce the portion of the index that has to be scanned". Together with the PostgreSQL 18 release notes below, that is the basis for the "PostgreSQL 18" pin on skip scan in section 6, which the trim added in place of "recent PostgreSQL" (verified retroactively).
- [PostgreSQL Documentation — 11.8. Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html) — the three legitimate uses, the predicate-implication requirement and the parameterized-predicate limitation, unique partial indexes for subset uniqueness, and the warning against many partial indexes as a substitute for partitioning.
- [PostgreSQL Documentation — 11.9. Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html) — requirements for an index-only scan including the visibility map, `INCLUDE` payload columns, and the "little point" warning for fast-changing tables.
- [PostgreSQL Documentation — CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html) — `CONCURRENTLY` semantics: cannot run inside a transaction block, two table scans, waiting on existing transactions, and the invalid index left behind on failure plus its recommended recovery.
- [PostgreSQL Documentation — ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html) — non-rewriting `ADD COLUMN` with a non-volatile default versus the volatile, generated, identity and constrained-domain cases that rewrite; `NOT VALID` plus `VALIDATE CONSTRAINT` and their lock levels; `SET NOT NULL` skipping the scan when a proving `CHECK` exists; combining subcommands into one statement; the strictest-lock rule; `DROP COLUMN` not reclaiming space; rewriting forms not being MVCC-safe; and the rule that a collation change forces an index rebuild.
- [PostgreSQL Documentation — 13.3. Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html) — the lock conflict matrix, `ACCESS EXCLUSIVE` being the only mode that blocks a plain `SELECT`, and lock waiters waiting indefinitely.
- [PostgreSQL Documentation — 19.11. Client Connection Defaults](https://www.postgresql.org/docs/current/runtime-config-client.html) — read 2026-09-28 (self-reported PostgreSQL 18.6), for the `lock_timeout` row in section 8's lock table (verified retroactively). Section 19.11.1 says `lock_timeout` will "Abort any statement that waits longer than the specified amount of time while attempting to acquire a lock", that the limit "applies separately to each lock acquisition attempt", and that "A value of zero (the default) disables the timeout", which is why section 8 calls lock waits unbounded by default. It also says that, "Unlike `statement_timeout`, this timeout can only occur while waiting for locks". The page does not name the SQLSTATE that the timeout raises. The source code below does.
- [PostgreSQL Documentation — Appendix A. PostgreSQL Error Codes](https://www.postgresql.org/docs/current/errcodes-appendix.html) — read 2026-09-28 (self-reported 18.6). It lists `55P03` as `lock_not_available` under Class 55 (Object Not In Prerequisite State), and `25P02` as `in_failed_sql_transaction` under Class 25 (Invalid Transaction State). These are the two codes in section 8's `lock_timeout` row. The appendix maps codes to names only and does not say which operation raises each one.
- [PostgreSQL source, REL_18_STABLE — `src/backend/tcop/postgres.c`](https://raw.githubusercontent.com/postgres/postgres/REL_18_STABLE/src/backend/tcop/postgres.c) — read 2026-09-28. `ProcessInterrupts` reports an expired `lock_timeout` as `ERRCODE_LOCK_NOT_AVAILABLE`, "canceling statement due to lock timeout". In an aborted transaction block, it rejects any statement other than `COMMIT`, `ROLLBACK`, `ROLLBACK TO SAVEPOINT` or `PREPARE TRANSACTION` with `ERRCODE_IN_FAILED_SQL_TRANSACTION`, "current transaction is aborted, commands ignored until end of transaction block". [`src/backend/utils/errcodes.txt`](https://raw.githubusercontent.com/postgres/postgres/REL_18_STABLE/src/backend/utils/errcodes.txt) maps those constants to `55P03` and `25P02`. The same day this was reproduced on a scratch PostgreSQL 14.20 cluster while another transaction held `ACCESS SHARE` on the table. `BEGIN; SET lock_timeout = '3s'; ALTER TABLE t ADD COLUMN c int;` failed after 3.0 s with `55P03`. Re-issuing the `ALTER`, and even `SELECT 1`, in the same transaction then failed with `25P02` until `ROLLBACK`. That is the basis for section 8's "rerun the whole migration". The one in-transaction exception is a retry after `ROLLBACK TO SAVEPOINT`, which succeeded in the same test. Section 8 does not mention it.
- [PostgreSQL Documentation — 14.1. Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) — `EXPLAIN ANALYZE` executing the statement, arbitrary cost units, `actual time`/`rows`/`loops` semantics, `ANALYZE` implying `BUFFERS` on this version (the [/docs/17/](https://www.postgresql.org/docs/17/using-explain.html) page shows `BUFFERS` merely as an option usable with `ANALYZE`, which is why section 7 says to write it explicitly), the `BEGIN`/`ROLLBACK` pattern for data-modifying statements, timing overhead and `pg_test_timing`, and the caveat that results do not extrapolate to other data sizes.
- [PostgreSQL Documentation — 14.4. Populating a Database](https://www.postgresql.org/docs/current/populate.html) — bulk-load ordering: one transaction, `COPY` over `INSERT`, indexes after loading, dropping and recreating foreign keys (including trigger event queue overflow), `maintenance_work_mem` and `max_wal_size`, then `ANALYZE`.
- [PostgreSQL Documentation — 5.12. Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) — the "table size exceeds server memory" threshold, the requirement that `PRIMARY KEY`/`UNIQUE`/`EXCLUDE` include all partition key columns, pruning from partition bounds, key selection from `WHERE` clauses and retention, the cost of too many partitions, hash being more future-proof than list, and `DETACH PARTITION CONCURRENTLY`.
- [PostgreSQL Documentation — 5.9. Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) — default-deny when enabled without a policy, `USING` vs `WITH CHECK`, permissive-OR vs restrictive-AND combination, owner exemption unless `FORCE ROW LEVEL SECURITY`, superuser and `BYPASSRLS` bypass, referential-integrity checks bypassing RLS as a covert channel, and `row_security = off`.
- [PostgreSQL Documentation — btree_gist](https://www.postgresql.org/docs/current/btree-gist.html) — appendix F numbering shifts as contrib modules come and go, so this entry is cited by name rather than section number. The GiST operator classes for B-tree-comparable types including `int4`, `int8` and `uuid`, and the `EXCLUDE USING GIST (cage WITH =, animal WITH <>)` example that establishes why an equality-plus-range exclusion constraint needs the extension.
- [MySQL 8.4 Reference Manual — CREATE INDEX](https://dev.mysql.com/doc/refman/8.4/en/create-index.html) — the "Functional Key Parts" section: MySQL indexes expressions directly, with the required extra parentheses (`CREATE INDEX idx1 ON t1 ((col1 + col2))`), which is the basis for correcting the cross-engine expression-index row in section 1. The [8.0 page](https://dev.mysql.com/doc/refman/8.0/en/create-index.html) supplies the version: "MySQL 8.0.13 and higher supports functional key parts that index expression values rather than column or column prefix values."
- [PostgreSQL 15 Documentation — Constraints](https://www.postgresql.org/docs/15/ddl-constraints.html) — documents the `NULLS NOT DISTINCT` clause. The [PostgreSQL 14 page](https://www.postgresql.org/docs/14/ddl-constraints.html) does not mention it and still describes null-distinct behaviour as conforming to the SQL standard; together these fix the PostgreSQL 15+ availability caveat in section 4.
- [PostgreSQL 18 Documentation — E.6. Release 18](https://www.postgresql.org/docs/18/release-18.html) — read 2026-09-28 (self-reported 18.6; release date 2025-09-25). These release notes independently confirm the three PostgreSQL 18 pins, each from the release that introduced it. Section E.6.3.1.2 lists "Allow skip scans of btree indexes", for multi-column indexes "when there are no restrictions on the first or early indexed columns" (section 6). Section E.6.3.2.3 lists "Automatically include BUFFERS output in EXPLAIN ANALYZE" (section 7). The release also adds "UUID version 7 generation function uuidv7()", with the `uuidv4()` alias added alongside (section 3). The trim turned the skip scan wording from "recent PostgreSQL" into this pin (verified retroactively). The `uuidv7()` and `BUFFERS` pins were already supported by the /docs/17/ comparisons above.
- [PostgreSQL 9.6 Documentation — E.25. Release 9.6](https://www.postgresql.org/docs/9.6/release-9-6.html) — read 2026-09-28 (self-reported 9.6.24; release date 2016-09-29; the page is marked as documentation for an unsupported version). These notes add "variadic functions num_nulls() and num_nonnulls()", and give the example "CHECK(num_nonnulls(a,b,c) = 1) which asserts that exactly one of a,b,c is not NULL". Section 2's polymorphic-parent `CHECK` uses that pattern, which the trim added (verified retroactively). Section 2 pins no version for it.
- [PostgreSQL Wiki — Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This) — community-maintained, not official documentation. The source specifically for the `char(n)`/`varchar(n)` and timestamp-`BETWEEN` advice, plus rejecting the `money` type, `timestamp(0)` rounding, identity columns over `serial` on PostgreSQL 10+, lower-case unquoted identifiers, `NOT IN` with nullable subqueries, and avoiding rules and table inheritance.
- [Use The Index, Luke! — Concatenated Keys](https://use-the-index-luke.com/sql/where-clause/the-equals-operator/concatenated-keys) — the leftmost-prefix rule, the telephone-directory analogy, and choosing column order so the index is usable as often as possible.
- [Use The Index, Luke! — Greater, Less and BETWEEN: access vs filter predicates](https://use-the-index-luke.com/sql/where-clause/searching-for-ranges/greater-less-between-tuning-sql-access-filter-predicates) — "Index for equality first — then for ranges", the access-predicate vs filter-predicate distinction, and why selectivity alone should not drive composite column order.
- [Use The Index, Luke! — Case-Insensitive Search](https://use-the-index-luke.com/sql/where-clause/functions/case-insensitive-search) — a function around an indexed column disabling that index, function-based indexes requiring the exact expression to appear in the statement, the computed-column route on SQL Server, and updating statistics afterwards. Its claim that MySQL also needs that route predates MySQL's own functional key parts; section 1 follows the current MySQL reference instead.
- [Use The Index, Luke! — Insert, Delete, Update](https://use-the-index-luke.com/sql/dml) — indexes as redundancy every write must maintain, and `INSERT` taking no direct benefit from any index.
- [SQL Performance Explained (book site)](https://sql-performance-explained.com/) — confirms Markus Winand's authorship and that the same content is readable free at use-the-index-luke.com, which is why the indexing rules above cite public URLs rather than page numbers.
- [ParallelChange — Danilo Sato (martinfowler.com)](https://martinfowler.com/bliki/ParallelChange.html) — expand / migrate / contract as three separately releasable phases, and its purpose of keeping old and new supported simultaneously; documented as a refactoring strategy by Joshua Kerievsky in 2006.
- [Evolutionary Database Design (Sadalage and Fowler)](https://martinfowler.com/articles/evodb.html) — database artifacts in the same version control repository as the application, every change as a migration script alongside the app change, a database instance per developer, database changes under continuous integration, and a transition period supporting both old and new access patterns for destructive changes.
- [SQL Style Guide (Simon Holywell)](https://www.sqlstyle.guide/) — the naming rules in section 13: snake_case, no reserved keywords, no `tbl_`/`sp_` prefixes, no table named the same as one of its columns, singular column names, the standard suffixes, the identifier-length house convention, and spelling out `AS`. Licensed CC BY-SA 4.0.
- [SQL Antipatterns, Volume 1: Avoiding the Pitfalls of Database Programming — Bill Karwin (Pragmatic Bookshelf)](https://pragprog.com/titles/bksap1/sql-antipatterns-volume-1/) — source of the antipattern names (trimmed from SKILL.md 2026-09-28), taken from the publisher's table of contents. No chapter text or page number was consulted, so nothing here is a quotation from the book.
- [RFC 9562 — Universally Unique IDentifiers (UUIDs)](https://www.rfc-editor.org/info/rfc9562) — current UUID specification, obsoleting RFC 4122; defines UUIDv7, recommends it over v1/v6, and supplies the index-locality quotations (trimmed from SKILL.md 2026-09-28) behind the UUIDv7 rule in section 3.
- [RFC 8259 — The JavaScript Object Notation (JSON) Data Interchange Format](https://www.rfc-editor.org/info/rfc8259) — current JSON standard (Internet Standard, STD 90), obsoleting RFC 7159, which the PostgreSQL JSON documentation still cites.

Normalization itself is stated here as general practice: no freely retrievable primary source was consulted, and no clause of ISO/IEC 9075 is cited. The soft-delete, audit-column and tenant-id-leading-key recommendations are likewise general practice — their mechanical justifications (partial unique indexes, leftmost-prefix indexing, composite foreign keys) come from the sources above, but the design recommendations are not attributed to any of them. The migration-runner transaction flags named in section 8, the backfill-bloat rule in section 9, the closure-table/materialized-path/`ltree` selection rule in section 2, and section 6's definition of a redundant index (a non-unique index on a leading prefix of another; added 2026-09-28 when the review checklist was folded into the body) are likewise general practice, stated from the mechanics documented above rather than quoted from any source; verify each flag's current spelling in its own tool's documentation.
