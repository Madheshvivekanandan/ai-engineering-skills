# API Contract Design Best Practices — Sources

Provenance for [`../SKILL.md`](../SKILL.md). This file is deliberately kept
out of the skill body so it costs no tokens at load time; read it to verify a
rule, not to follow one. Repository-wide provenance tiers and known gaps:
[SOURCES.md](../../../SOURCES.md).

Throughout this file, "this document" and section references like §4 point to
`../SKILL.md`, whose rules these sources support. This text was moved out of that
file verbatim, so "the rules above" likewise means the rules there.


Primary sources retrieved and read while writing this document:

- [RFC 9110 §9 — HTTP Semantics: Methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9) — definitions of safe, idempotent, and cacheable; the method-properties table in §3; the `PUT`-as-full-replacement vs `POST`-as-server-defined-processing distinction.
- [RFC 9110 §15 — Status Codes](https://www.rfc-editor.org/rfc/rfc9110.html#section-15) — the status table in §4. Verbatim quotations: "The server generating a 401 response MUST send a WWW-Authenticate header field ... containing at least one challenge applicable to the target resource" (§15.5.2); "The origin server MUST generate an Allow header field in a 405 response containing a list of the target resource's currently supported methods" (§15.5.6). Also `409` vs `412`, `422`, and the rule that unrecognized codes are interpreted by class. Note what §15.3.2 (`201 Created`) does **not** say: it carries no `SHOULD` for `Location`, only that the created resource "is identified by either a Location header field in the response or, if no Location header field is received, by the target URI".
- [RFC 9110 §9.3.3 — POST](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.3) — the actual normative source for `Location` on creation: "the origin server SHOULD send a 201 (Created) response containing a Location header field that provides an identifier for the primary resource created" — which is why §4 marks `Location` as a house-tightened MUST.
- [RFC 9110 §13 — Conditional Requests](https://www.rfc-editor.org/rfc/rfc9110.html#section-13) — `ETag` and `Last-Modified` validators, strong vs weak, the four precondition headers and their evaluation order, `412` vs `304`, and the lost-update pattern behind §12.
- [RFC 5789 — PATCH Method for HTTP](https://www.rfc-editor.org/rfc/rfc5789.html) — Standards Track, March 2010. "PATCH is neither safe nor idempotent"; clients "using this kind of patch application SHOULD use a conditional request such that the request will fail if the resource has been updated since the client last accessed the resource", for example a strong ETag in `If-Match` (the RFC scopes this to patch formats needing a known base-point, and exempts append-style patches; §3 rule 6 tightens it to all `PATCH`); and there is "no single default patch document format that implementations are required to support" — the basis of §3 rules 5 and 6.
- [RFC 6585 — Additional HTTP Status Codes](https://www.rfc-editor.org/rfc/rfc6585.html) — Standards Track, April 2012, not obsoleted. §3 `428 Precondition Required` ("the origin server requires the request to be conditional"), §4 `429 Too Many Requests` (whose response "MAY include a Retry-After header"). Neither code appears in RFC 9110.
- [RFC 9457 — Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html) — the error format: `application/problem+json`, the five standard members and their exact semantics, extension-member naming, the requirement that consumers ignore unrecognized extensions, the `about:blank` default, the IANA problem-type registry, and the security requirement not to expose stack dumps. **Obsoletes RFC 7807.**
- [RFC 7396 — JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396.html) — `application/merge-patch+json`, `null` as delete, whole-array replacement, and its unsuitability for documents with meaningful explicit nulls.
- [RFC 6902 — JSON Patch](https://www.rfc-editor.org/rfc/rfc6902.html) — `application/json-patch+json`, the six operations, and the requirement that a failing operation means the whole patch is not applied.
- [RFC 9745 — The Deprecation HTTP Response Header Field](https://www.rfc-editor.org/rfc/rfc9745.html) — Standards Track, March 2025. `Deprecation` as a Structured Field Item carrying a date (`@1688169599`), which may be past or future and changes no behavior; the requirement that a `Sunset` value not precede it; the `deprecation` link relation.
- [RFC 8594 — The Sunset HTTP Header Field](https://www.rfc-editor.org/rfc/rfc8594.html) — Informational, May 2019. `Sunset = HTTP-date` (`Sunset: Sat, 31 Dec 2018 23:59:59 GMT`), applying to the resource that returns it, and that clients "SHOULD treat Sunset timestamps as hints" — the syntax and status used in §11.
- [RFC 8288 — Web Linking](https://www.rfc-editor.org/rfc/rfc8288.html) — `Link` header syntax; §2.1.2, that an *extension* relation type "is a URI ... that uniquely identifies the relation type", SHOULD be under the control of whoever defines it, and SHOULD be all-lowercase. Registered relation types (§2.1.1) are bare tokens — the basis of the §9 link-relation row.
- [OpenAPI Specification (latest)](https://spec.openapis.org/oas/latest.html) — current release v3.2.0, 19 September 2025; the top-level object fields including `webhooks` and `components`; `info` requiring `title` and `version`.
- [OpenAPI Specification v3.1.0](https://spec.openapis.org/oas/v3.1.0.html) — confirms the top-level `webhooks` field for out-of-band, non-API-initiated requests, and the `securitySchemes`/`security` mechanism used in §10 and §15.
- [Migrating from OpenAPI 3.0 to 3.1.0](https://www.openapis.org/blog/2021/02/16/migrating-from-openapi-3-0-to-3-1-0) — the Schema Object aligned to JSON Schema 2020-12 (3.0 was Draft 05), `nullable` removed outright, and the singular `example` replaced by the `examples` array.
- [draft-ietf-httpapi-ratelimit-headers — RateLimit header fields for HTTP](https://www.ietf.org/archive/id/draft-ietf-httpapi-ratelimit-headers-11.html) — `RateLimit-Policy` (`q` required, plus `qu`, `w`, `pk`) and `RateLimit` (`r` required, plus `t`, `pk`), the examples reproduced in §13, the `Retry-After` precedence rule, and the non-normative appendix listing the `X-RateLimit-*` conventions in current use and their interoperability problems. **An Internet-Draft, not an RFC.**
- [Google AIP-158 — Pagination](https://google.aip.dev/158) — the page-size/page-token/next-page-token contract, coercing oversize page sizes down, opaque tokens that must never confer authorization, an empty token as the only end-of-collection signal, optional and possibly estimated totals, and that adding pagination to an existing method is backwards-incompatible.
- [Google AIP-193 — Errors](https://google.aip.dev/193) — messages actionable for a technical reader and free of PII and internal implementation detail, plus machine-readable `UPPER_SNAKE_CASE` reason codes with domain and metadata (mapped here onto problem+json extension members rather than importing the gRPC envelope).
- [Google AIP-180 — Backwards compatibility](https://google.aip.dev/180) — the enumeration behind §11: removals and renames, type changes, newly required fields, changed defaults and default serialization, changed identifier formats, changed observable semantics, and the caution about adding response enum values.
- [Google AIP-136 — Custom methods](https://google.aip.dev/136) — colon-suffixed custom methods on the resource path, when they are justified over standard methods, and `GET` only for side-effect-free ones.
- [Zalando RESTful API Guidelines](https://opensource.zalando.com/restful-api-guidelines/) — the numbered MUST/SHOULD/MAY format and its positions on API-first, one self-contained spec, backward compatibility and tolerant readers, casing conventions, ETags, problem JSON, no stack traces, `Deprecation`/`Sunset` with monitoring, cursor-over-offset pagination, and `Idempotency-Key`. Rule titles verified verbatim: 113 "SHOULD avoid versioning", 114 "MUST use media type versioning", 115 "MUST not use URL versioning" — the source of the media-type option in §11. Rule 176 "MUST support problem JSON" cites RFC 9457 (verified in the page source; the rendered page truncates in some fetchers), consistent with §5.
- [Azure REST API Guidelines (microsoft/api-guidelines, vNext/azure)](https://raw.githubusercontent.com/microsoft/api-guidelines/vNext/azure/Guidelines.md) — URL and casing rules, `403` vs `404` for existence leaks, "never 404 for DELETE", omitting rather than nulling absent members and the last page's continuation link, the `202`-plus-status-monitor pattern with a 24-hour retention floor and the `Operation-Location` header carrying the monitor URL, the required dated `api-version` parameter, `Repeatability-Request-ID`, and its own non-problem+json error envelope. Presented here as a competing house style, not as consensus.
- [Stripe — Idempotent requests](https://docs.stripe.com/api/idempotent_requests) — the `Idempotency-Key` pattern: the first request's status and body stored and replayed including failures, UUIDv4 keys up to 255 characters with no sensitive data, parameters compared against the original, keys pruned after at least 24 hours, and results deliberately not saved for validation failures or concurrent collisions. Product decisions, cited as sane defaults.
- [Stripe — Webhooks](https://docs.stripe.com/webhooks) — the production webhook contract: HTTPS with TLS 1.2/1.3, timestamped HMAC-SHA256 signatures over the raw body with constant-time comparison and rejection of non-current schemes, a 5-minute default tolerance, secret rotation with overlap, "quickly return a successful status code (`2xx`) prior to any complex logic that could cause a timeout" with events processed on an asynchronous queue, at-least-once and unordered delivery with dedupe on event id, retries with exponential backoff, `3xx` treated as failure, and version-pinned immutable events. Also defaults, not standards.
- [OWASP API Security Top 10 — 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) — the categories cited in §10: API1 broken object level authorization, API3 broken object property level authorization, API4 unrestricted resource consumption, API9 improper inventory management, API10 unsafe consumption of APIs.
- [oasdiff — Preventing Breaking Changes](https://github.com/oasdiff/oasdiff/blob/main/docs/BREAKING-CHANGES.md) — the `breaking` and `changelog` subcommands, and the documented requirement that `--fail-on ERR` (or `WARN`/`INFO`) is what makes `breaking` "exit with return code 1"; without it the command reports and exits 0. This is the gate that mechanizes §11.
- [Spectral](https://github.com/stoplightio/spectral) — `spectral lint <file> [--ruleset ...]`, the built-in `spectral:oas` ruleset, and `extends` in `.spectral.yaml` (all from the README). The `--fail-severity` flag used in §16 is not in the README; it is defined in `packages/cli/src/commands/lint.ts` with choices `error|warn|info|hint` and default `error` — confirm it for the version you install.
